# BacklinkOS 正式外链提交流程规范 (Formal Submission Workflow)

> **唯一权威来源**：本文档定义 BacklinkOS 的正式外链提交流程，所有 AI 宿主入口（`AGENTS.md`、`GEMINI.md`、`CLAUDE.md`、`README.md`）均以本文档为准。

> [!IMPORTANT]
> ## 2026-09-20 当前控制面分类规则（覆盖本文较早的业务分类表述）
>
> `外链总表` 的用户可见分类层使用 O:R：`状态 / 淘汰原因 / 平台类型 / 获取方式`。
>
> - `状态` 只允许空白或 `可用`。空白就是尚未完成验证的候选，不再写“候选”。
> - `淘汰原因` 非空即进入黑名单。当前个人业务策略下，明确死站/无可执行外链入口/垃圾或低质量来源/**纯付费-only** 均可淘汰；疑似、未知、未验证不得淘汰。
> - 项目级不兼容不自动淘汰平台。MCP-only、Agent-only、本地商家、优惠券、地域限制、需互链等，只要平台本身存在真实可执行渠道，仍可标 `可用`，并把明确限制写入平台事实。
> - `外链管理` 中真实执行产生的证据必须反向沉淀到 Master。项目状态为 `已提交 / 审核中 / 已排期 / 已上线` 时，可确认 Master `状态=可用`；`需人工` 只有在已经验证真实 submission entry/auth wall 时才可确认 `可用`。
> - 平台事实坚持 **known-only**：提交入口、免费/付费、登录、登录方式、限制、平台类型、获取方式都只写明确证据；未知留空。经过历史真实浏览器执行并保存在 `外链管理.证据摘要` 的可核验事实，可以用于 Master 回灌；普通历史备注、Discovery 标签、猜测不能。
> - `实测链接属性` 仍要求公开 listing 已上线并直接检查目标 `<a>` 的 DOM `rel`；否则必须为空。
> - A:N 中的 `基础状态/基础排除原因` 保留为隐藏技术兼容列，供现有脚本门禁使用，不作为用户日常分类。业务 `状态=可用` 的行技术状态仍可保持 `候选`；业务黑名单行的技术状态为 `已排除/失效`。
>
> 当前单用户控制面的“纯付费-only”淘汰策略优先于本文旧版“由各项目分别决定”的通用化设计。

## 1. 核心定位与使用模式

在已配置浏览器和 Google Sheets 权限的 AI 环境中，用户在一个**完全没有历史记忆的新会话**中，只需输入类似：

```text
按本项目正式流程，为 quick-iching 提交外链，本轮目标新增成功提交 200 个。
```

AI 即可自动识别正式入口，闭环完成：
**读取候选快照 → 自动有界准备 (Phase C) → 分批提交 (Phase D) → 记录与回读 → 跨项目排除同步 → 继续下一批**，直至达到成功目标或本轮候选快照耗尽。

**核心红线：**
1. **不要求用户手动操作**：不要求用户手动生成 Ready 清单、手动运行准备脚本、解释状态规则或提供历史聊天记录。
2. **实际提交由当前 AI 驱动**：`backlink-autofill` 并不存在外部黑盒自动提交所有站点的独立脚本；真实提交由**当前会话的 AI** 依据 `backlink-autofill` 插件与 `browser_cli` 驱动 Playwright 浏览器执行。模拟结果仅用于测试，严禁作为正式提交路径。
3. **有限范围与双边界**：整次运行以启动时选定项目的待提交候选快照为上限范围，最多覆盖一轮；达到目标或快照耗尽即停止，绝不为了凑够数量无限扩扫或死循环。
4. **运行进度全持久化**：运行快照、批次进度、检查结果、待人工事项（HUMAN_PENDING）持久化在磁盘（`~/.backlinkos/runtime/cycles/<project_id>/`），新会话可无缝恢复。
5. **严谨的“新增成功提交”定义**：仅统计本轮实际产生并已写回 Sheet 确认的 `已提交`、`审核中`、`已排期`、`已上线` 行；不包括 Ready 状态、填完表单未确认、查重发现的历史已有提交；同一次尝试恢复也不重复计数。

## 2. 核心架构与数据流

```text
启动运行（锁定项目候选快照）
         ↓
【Phase C — Bounded Execution Preparation】
检查当前批次 Ready 清单；若无，自动执行有界现场核验 (prepare_execution_batch)
仅对核验通过的项更新【外链总表.提交入口】，产出当前批次 Ready Allowlist Manifest
         ↓
【Phase D — backlink-autofill 实际提交执行】
当前会话 AI 读取 Ready Allowlist 与项目待提交交集
逐行执行：Gate 校验 → Preflight 查重防重复提交 → 真实浏览器表单填写 → 邮箱 OTP 自动处理
遇到验证码/支付等真阻碍：保存现场为 HUMAN_PENDING，保留标签页，不阻塞批次继续
         ↓
【结果回写与精确回读】
通过 ProductionSheetGate 校验，精确定位项目行写回状态与证据并立即 read-back 验证
         ↓
【排除研判与跨项目排除同步】
若发现全局不可用（死站、关闭收录）：写总表已排除/失效，并同步其他项目尚未开始的“待提交”行
项目不兼容（如 AI-only）：仅写当前项目不适用，总表记录事实，不连带排除其他项目
付费-only：总表记录实测非免费事实，由各项目政策分别决定
         ↓
【进度更新与自动批次循环】
更新持久化 Cycle 状态与累计新增成功数
若成功数 < 目标 且 快照仍有剩余候选 → 自动进入下一批次
若达到目标 或 快照耗尽 → 输出对账清单并结束
```

## 3. 详细执行规则

### 3.1 候选准备与提交衔接 (Phase C → Phase D)
1. **自动衔接**：当 `外链管理` 中只有项目待提交行，但没有已核验的 Ready 清单时，正式入口自动调用 `scripts/prepare_execution_batch.py`，单批扫描有界候选（如 `target_ready_count=10`，`scan_limit=50`）。
2. **核验通过才进入 Ready**：
   - 验证成功：产出 `VerifiedEntry`，更新 `外链总表.提交入口`，加入当前批次 `Ready Allowlist`；
   - 验证失败或未解决（unresolved）：项目行保持 `待提交`，状态不变，`尝试次数` 保持 0，不标失败，继续下一候选；
3. **严格消费交集**：提交执行阶段严格只消费 `(项目ID == selected_project AND 状态 == 待提交)` 与 `Ready Allowlist` 的交集。绝不从未经验证的 3000+ 底池中直接消费。

### 3.2 排除分类与跨项目同步 (Cross-Project Sync)
所有排除必须有逐项证据和明确适用范围，严禁混淆：

| 排除类别 | 典型场景 | 总表处理 | 当前项目处理 | 其他项目同步行为 |
| --- | --- | --- | --- | --- |
| **平台全局不可用** | 平台彻底关闭收录、永久下线、死站、明确对全行业禁入 | 基础状态设为 `已排除`（附原因）或 `失效` | 设为 `不适用` 或 `失败` | **允许有限跨项目同步**：将其他项目中**处于“待提交”状态**的对应行同步更新为 `不适用` 或 `失败`。严禁修改非待提交历史行，严禁复制项目私有信息。 |
| **项目专属不兼容** | 平台仅收录 AI 工具，而当前项目是非 AI（如 Quick I Ching） | 基础状态**保持候选**；在平台备注/实测限制记录“仅限AI工具” | 设为 `不适用`（原因：项目不兼容） | **绝不连带排除**！AI 项目依然正常使用该平台。 |
| **纯付费-only（当前个人策略）** | 已明确不存在任何免费/换链/条件免费路径，只能付费 | 当前控制面将其作为业务黑名单：`淘汰原因=纯付费`，技术兼容列设为 `已排除`，并记录 `实测免费=非免费` | `不适用` | 新项目不再投影；已有历史状态不覆盖，尚未执行的行会被 Master Gate 阻断。若仅某一套餐付费、仍存在免费例外，则不属于 paid-only。 |
| **未知/暂时性异常** | 网络超时、读取不完整、入口未找到 | 基础状态**保持候选**；提交入口留空 | 保持 `待提交`，尝试次数 0 | **绝对不作为永久排除理由**，不向其他项目传播。 |

**跨项目同步落表 5 大守卫：**
1. **稳定键定位**：基于稳定的 `项目ID + 外链ID` 定位目标行；
2. **写前核实当前状态**：必须先回读当前行，严格仅当当前状态仍为 `待提交` 时才允许执行同步；任何已提交、审核中、已排期、已上线、需人工、处理中记录绝对保护；
3. **门禁校验**：更新载荷必须通过 `ProductionSheetGate` 校验；
4. **实际写回与精确回读**：更新单元格后立即回读，核验写入值一致；
5. **记录受影响项目结果**：输出受影响项目明细；若部分写入失败，记录到 `pending_cross_project_sync.json` 供后续安全恢复。同时后续项目在打开网站前通过 Master Gate 检验总表，防守双保险。

### 3.2.1 平台事实自动沉淀与跨项目复用机制 (Platform Facts Writeback & Reuse)
为彻底杜绝项目 A 确认平台事实后项目 B 重复踩坑（重复探加入口、误访已否定错误入口、重复研判已知限制），系统建立**双向自动流转机制**：

1. **项目执行阶段事实自动沉淀**：
   - 当前 AI 在调用 `record-outcome` 记录结果时，除项目状态外，必须将实测确认的平台事实传入 `--platform-facts`（JSON 字符串或字典）；
   - **有效入口**：成功提交或核实到的规范提交 URL，回写总表【提交入口】；
   - **否定入口**：实测发现的错误入口（如商品加购页、房源咨询、作者招募等），若总表现有入口等于该错误路径，**立即清空总表提交入口**，并在【平台备注】追加 `否定入口: <url> (<原因>)`；基础状态严格保持为 `候选`（禁止因单个入口错误将平台标为失效）；
   - **实测限制与属性**：实测限制（如 `纯付费收录`）、实测免费（`免费`/`非免费`）、实测需登录（`是`/`否`）、登录方式（如 `Google OAuth`）统一沉淀入总表对应列；写回时**合并保留已有事实，严禁盲目覆盖**；
   - **最后验证时间**：每次事实沉淀自动记录精确到秒的 ISO 观察时间戳。

2. **后续项目跨会话无缝复用**：
   - 后续项目（如项目 B）启动时，`prepare_execution_batch` / `plan_next_batch` 优先复用总表中已沉淀的有效入口，直接进入 Ready 清单，无需重复耗时探测；
   - **否定入口智能避让**：总表已记录的否定入口自动被过滤排除，准备阶段不再探测该已知错误路径；
   - **项目属性独立判断与未知安全守卫**：
     - 未知属性严格保持为 `None`，**绝不因为“未声明”而默认假设为否定**（未声明预算不代表不接受付费，未声明 AI 不代表非 AI）；
     - 当前个人控制面若已明确证实为 **纯付费-only**（没有任何免费、换链或条件免费路径），直接进入业务黑名单；如果只是某个套餐收费、存在免费例外或是否有免费路径尚不明确，则保持候选/可用事实，不得误判为 paid-only；
     - 仅当项目权威配置明确声明 `ai_powered=False` 且总表证实排他限制（`仅限AI`）时才做兼容性排除；
     - 属性未知或政策兼容的项目绝不连带排除，完全独立判断。

3. **全局待恢复队列保障 (Pending Mutations Recovery)**：
   - 若向 Google Sheet 回写总表事实遭遇网络超时或 503 等异常，变更原子持久化至全局共享 `~/.backlinkos/runtime/pending_master_mutations.json`；
   - **不影响当前项目进度**：当前项目的提交状态与尝试次数已落表核验，绝不回滚，绝不增加尝试次数；
   - **新会话自动发现与跨项目恢复**：新会话启动任意项目（无论是 A 还是 B）时，编排器首先自动扫描全局与各 cycle pending 文件，自动执行写前核实与写后全字段整行回读比对，成功落表后原子移除。

### 3.3 人工事项非阻塞与断点恢复
1. **遇到真阻碍立即挂起**：遇到 CAPTCHA/Cloudflare、2FA/SMS/验证码、强制支付、复杂授权时：
   - 保留当前 headed 浏览器可见标签页，获取真实的 CDP `target_id`；
   - 调用规范的 `save_human_pending` 生成独立交接记录至 `~/.backlink-autofill/runtime/human-pending/{project_id}/{backlink_id}.json`（严格无凭据）；
   - 调用 `record-outcome --status 需人工 --target-id <id>`；
   - **现场待重建机制 (needs_rebuild)**：若因浏览器崩溃、重启或用户关闭导致 CDP 目标丢失，系统将 `live_tab_available` 标为 False，`checkpoint_ref` 标为 `needs_rebuild`，输出重新打开入口并导航至目标页面的指引，绝不伪造在线标签页；
   - **明确向用户输出指引**（站点、阻碍类型、需完成动作），**立即继续处理当前批次的其他候选**，绝不中断批次；
2. **用户处理与恢复**：用户可在途中或批次结束后处理该标签页。用户告知处理完成后：
   - 调用 `start-attempt --resume-same-attempt` 恢复同一次尝试；
   - **不递增 `尝试次数`**；
   - **首次提交成功正常计入新增成功**（仅针对同一尝试二次上报成功时防重，不重复计入）；
   - 严禁点击最终提交后结果不明确时自动重试。
3. **用户操作隔离**：用户在处理某个保留标签页时，AI 绝不同时操作该标签页。

### 3.4 批次组织与全量状态对账
- 单批处理完成后，编排器更新累计成功数；
- 若未达目标且候选快照有剩余，自动启动下一批准备与提交；
- **探测账本冷却期与跨轮次复用**：Phase C 探测账本（`scan_ledger`）持久化事实（如无入口、否定入口），并在跨轮次启动时支持冷却期机制（默认 7 天）。冷却期内已确认无入口或否定入口的条目自动跳过盲探，到期后可重新核验；超时项始终保持为未知/候选，实现快速准备且不漏掉新开放收录的平台；
- 循环退出条件（满足其一即停止）：
  1. `累计新增成功 >= 目标成功数`；
  2. `本轮候选快照已扫描一轮耗尽`。
- **显式中断记录 (record-interruption)**：若中途因外部异常、用户指令或预算提前停止，必须调用 `record-interruption` 记录明确原因（查不明记为“未知中断”，严禁随意猜测）；新会话恢复运行时将显式展示上一次中断原因；绝不把“对账平衡”当作“任务完成”；
- 退出时输出完整对账表：
  $$\text{总责任快照数} = \text{新增成功数} + \text{历史已有数} + \text{不适用数} + \text{失败数} + \text{需人工数} + \text{仍待提交数}$$
  总责任快照数在跨轮启动时包含当前项目待提交候选与继承的未决人工项，所有分类完全互斥独立，账目严丝合缝，绝不虚报完成。

## 4. 宿主与执行工具指引

### 4.1 CLI 编排支撑工具
系统提供 `scripts/run_submission_cycle.py`，作为会话状态机和批次编排支撑：
```bash
# 启动或恢复指定项目的提交循环（例如目标 200 个）
python3 scripts/run_submission_cycle.py --project-id quick-iching --target-success 200

# 在驱动真实浏览器前调用 start-attempt 进入处理中并累加尝试次数
python3 scripts/run_submission_cycle.py start-attempt --project-id quick-iching --backlink-id <bid> [--resume-same-attempt]

# 真实执行完成或遇到阻碍时调用 record-outcome 写回终态并自动沉淀平台事实
python3 scripts/run_submission_cycle.py record-outcome --project-id quick-iching --backlink-id <bid> --status <status> --reason "<原因>" --evidence "<证据>" [--platform-facts '{"entry_url": "...", "free": "免费", "requires_login": "否"}']

# 提前中止或遇到外部中断时记录明确中断原因
python3 scripts/run_submission_cycle.py record-interruption --project-id quick-iching --reason "<明确中断原因>"
```
该工具负责：
- 锁定候选快照，管理持久化状态与中断原因；
- 调用 Phase C 自动进行现场核验与总表回写（已有入口优先校验，整站探测总预算保护，细粒度 scan_ledger 沉淀与跨轮次冷却期复用）；
- 产出当前批次的 Ready 清单；
- 提供 `start-attempt` 门禁与 `record-outcome` 尝试次数严格落表回读校验；
- 在 `record-outcome` 中严格校验并自动沉淀平台事实至【外链总表】（有效入口更新、错误否定入口清除、实测限制合并、需登录/免费事实沉淀），并在 API 异常时落入全局待恢复队列；
- 遭遇人工阻碍联动持久化 `human-pending` 交接记录（支持 `needs_rebuild` 断点现场标识）；
- 提供跨项目全局排除同步接口与对账总结。

### 4.2 当前会话 AI 的标准操作动作
AI 在会话中收到指令后：
1. 运行 `run_submission_cycle.py` 获取当前批次与待处理 Ready 候选；
2. 针对每个 Ready 候选：
   - **开始尝试门禁**：先执行 `run_submission_cycle.py start-attempt`，将项目表状态置为 `处理中` 且 `尝试次数 +1`（断点恢复保持不变）；
   - **真实浏览器驱动**：依照 `backlink-autofill` 规范调用 `browser_cli` 驱动 Playwright 浏览器执行真实提交；
   - **阻碍交接**：若遇 CAPTCHA/登录墙等真阻碍，保留可见标签页，调用 `record-outcome --status 需人工 --target-id <id>`（自动落成交接 JSON），告知用户指引后继续处理下一候选；
   - **终态同步与事实沉淀**：提交成功或确认失败/不适用时，调用 `record-outcome` 记录真实结果，并将实测确认的平台事实（有效入口、否定入口、实测免费、实测需登录、登录方式等）传入 `--platform-facts`，自动安全沉淀至【外链总表】并回读校验，供其他项目复用；
3. 当前批次完成后，自动继续推进下一批，直至目标达成或快照耗尽；若因特定原因提前中止，必须调用 `record-interruption` 记录明确的中断原因，绝不虚假结案。
